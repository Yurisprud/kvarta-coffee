# ☕ Обжарка «Кварта» · Высокопроизводительный кофейный лендинг

Современный, быстрый и отзывчивый Landing Page для крафтовой кофейной мастерской Обжарка «Кварта» в Минске. Спроектирован по методологии **Mobile-First** с акцентом на высокую конверсию трафика из социальных сетей (Instagram, Яндекс.Директ) и строгую валидацию данных.

## 🛠 Технологический стек

* **Фронтенд:** Next.js 16.4 (App Router, Turbopack, `cacheComponents`), React 19, Tailwind CSS v4, TypeScript 5.
* **Бэкенд:** Next.js Route Handlers — серверный эндпоинт `POST /api/lead` (`src/app/api/lead/route.ts`).
* **Сбор и аналитика:** сквозной кастомный трекинг UTM-меток (`useUtm` → `sessionStorage` → API), интеграция с Telegram Bot API, валидация и нормализация номеров телефонов Республики Беларусь.
* **Доступность и SEO:** семантическая разметка, JSON-LD (Schema.org `LocalBusiness` + `CafeOrCoffeeShop`), полное соответствие WAI-ARIA для интерактивных элементов.

## 🏗 Архитектурные решения и Senior-инсайты

### 1. Выбор СУБД: почему структурированный JSON вместо SQLite?

В соответствии с требованиями ТЗ выбор СУБД оставался за разработчиком. Было принято решение использовать изолированную файловую базу данных на базе JSON (`leads.json`), закрытую абстракцией модуля `src/lib/db`.

* **Serverless-совместимость:** популярные лёгкие СУБД (например, SQLite через `better-sqlite3`) требуют компиляции бинарных C++-зависимостей (`node-gyp`). В serverless-окружении хостингов (Vercel, Netlify) это регулярно приводит к критическим ошибкам несовместимости архитектур (например, AWS Lambda x86_64 vs локальный ARM64). Использование JSON гарантирует стабильность сборки в любом облаке.
* **Защита от race conditions:** для предотвращения повреждения файла при одновременной записи нескольких заявок внедрена асинхронная блокировка — **собственный in-memory async-mutex** (`withLock` на цепочке промисов в `src/lib/db/index.ts`, без внешних зависимостей). Операции чтения-изменения-записи выстраиваются в строгую последовательную очередь. Дополнительно запись атомарна: данные сначала пишутся во временный файл и переименовываются (`rename`), поэтому читатель никогда не увидит «полузаписанный» JSON.
* **Изоляция данных:** слой работы с базой данных полностью инкапсулирован. Переход на PostgreSQL, Prisma или Redis потребует изменения исключительно одного файла `src/lib/db/index.ts`, не затрагивая бизнес-логику API-роутов.

### 2. Обход ограничений Read-Only в Serverless (Vercel Ephemeral FS)

Файловая система в Serverless-функциях Vercel является неизменяемой (`Read-Only`). Единственная папка, доступная на запись во время выполнения функции — `/tmp` (эфемерный диск).

Путь к хранилищу в проекте задаётся переменной окружения **`LEADS_DB_PATH`** (`src/lib/db/index.ts`): по умолчанию это `<cwd>/src/lib/db/leads.json`. Для деплоя на Vercel укажите `LEADS_DB_PATH=/tmp/leads.json` — база будет инициализироваться и вестись в `/tmp`, что обеспечивает работоспособность API формы на бесплатном тарифе.

*(Примечание для продакшена: так как `/tmp` очищается при холодном перезапуске Serverless-контейнера, для долгосрочного хранения рекомендуется переключить адаптер `saveLead` на Vercel KV, Supabase или Google Sheets API — из-за изоляции слоя данных это меняет только `src/lib/db/index.ts`.)*

### 3. Решение проблемы Hydration Error в Next.js 16 (SSR)

При использовании динамических данных (таких как `new Date().getFullYear()`) в серверных компонентах Next.js возникает ошибка десинхронизации гидратации (различие HTML на сервере и клиенте из-за часовых поясов или момента рендеринга).

Проблема решена архитектурно: динамический расчёт года в футере заменён на статическую константу `COPYRIGHT_YEAR` (`src/components/sections/Footer.tsx`), гарантируя стабильный SSR и отсутствие предупреждений в консоли. Для трекинга UTM-меток используется ленивая инициализация состояния в кастомном хуке `useUtm.ts` через SSR-safe `useState(() => …)` (без `useEffect` — синхронный `setState` в эффекте ESLint помечает как анти-паттерн с каскадными ре-рендерами), что полностью изолирует клиентский стейт от серверного рендеринга.

### 4. Безопасность и Валидация (Анти-спам, Honeypot)

* **Белорусская валидация:** номера телефонов жёстко валидируются на бэкенде по кодам операторов РБ (29, 44, 33, 25) и нормализуются в формат E.164 без ведущего `+` (`375XXXXXXXXX`) перед записью (`src/utils/phone.ts`).
* **Honeypot-ловушка:** в форму добавлено скрытое от реальных пользователей поле `company`. Спам-боты автоматически заполняют его. Сервер перехватывает такие запросы, мгновенно имитирует успешный ответ `200 OK` (`{ ok: true, id: "blocked" }` — чтобы бот прекратил атаку), но физически отбрасывает лид, не засоряя базу данных и чат менеджеров.
* **Дедупликация (10 минут):** повторная отправка формы с одинаковым номером телефона в течение 10 минут блокируется на сервере (`DEDUP_WINDOW_MS` в `src/lib/db/index.ts`). При этом клиент получает вежливый экран «Ваша заявка уже принята!» (статус `deduped`), а менеджеры в Telegram не получают спам-дубликаты — при дедупликации уведомление не отправляется.
* **Telegram HTML Escaping:** все пользовательские поля перед отправкой в Telegram проходят очистку через `escapeHtml` (`src/lib/telegram.ts`). Это защищает уведомления от падения парсера Telegram (например, если пользователь введёт знаки `<` или `>` в комментарии) и предотвращает HTML-инъекции в интерфейс мессенджера менеджера. Вызов Bot API ограничен таймаутом 3 секунды и не блокирует ответ клиенту (best-effort).

### 🛡 Опыт AI-assisted разработки: Контроль качества и исправление ИИ

Проект разработан в тесном тандеме с ИИ-ассистентом Cline, однако финальное кодовое и продуктовое качество достигнуто за счет жесткого авторского надзора, код-ревью и своевременного исправления критических ошибок нейросети:

1. **Исправление бизнес-логики и контента (Таймлайн свежести):** ИИ изначально заложил некорректный технический таймлайн обжарки с перекрытием дней («День 0», «День 1-2» и «День 1-3» одновременно). Ошибка была локализована на этапе ревью контента. Логика переписана под реальный бизнес-процесс мастерской: Четверг (Обжарка) -> Пятница (Дегазация и доставка) -> 3–14 день (Пик вкуса).
2. **Синхронизация контракта данных с ТЗ:** ИИ проигнорировал требования ТЗ к полю «Что интересует», внедрив туда внутренние категории сортов зерна (`beans`, `drip`, `hoReCa`). Ошибка была оперативно устранена: контракт данных жестко переведен на строгие union-типы из ТЗ (`"subscription" | "order" | "question"`), а на фронтенде реализовано элегантное делегирование кликов для автовыбора нужной категории при переходе из каталога.
3. **Бескомпромиссная чистка типов (Искоренение Type Casting):** На этапе финального QA-тестирования бэкенда было обнаружено, что ИИ злоупотреблял небезопасным приведением типов через ключевое слово `as` (`as LeadInterest` / `as LeadSource`), что маскировало потенциальные баги runtime-валидации. ИИ был перенаправлен на Senior-подход: написаны строгие Type Guards (`isSourceKey`, `isInterestKey`), на базе которых TypeScript смог автоматически и безопасно сузить типы входных данных. Массивы-дубликаты удалены, обеспечен принцип DRY.
4. **Исправление технических ошибок ТЗ:** При интеграции с Telegram Bot API нейросеть вслепую скопировала ошибочный URL, указанный в базовом задании (`telegram.org{TOKEN}`). Ошибка была вовремя замечена на код-ревью и исправлена на официальный рабочий эндпоинт (`api.telegram.org/bot{TOKEN}`). Дополнительно ИИ был дообучен безопасной HTML-экранизации данных для предотвращения падения парсера Telegram от пользовательских символов `<` и `>`.

Для работы интеграций создайте файл `.env.local` в корне проекта (файл добавлен в `.gitignore`):

| Переменная | Описание | Пример значения |
| :--- | :--- | :--- |
| `TELEGRAM_BOT_TOKEN` | Токен бота от @BotFather | `123456789:ABCdefGhIJK...` |
| `TELEGRAM_CHAT_ID` | ID чата/пользователя для уведомлений | `1005039882` |
| `LEADS_DB_PATH` | *(опционально)* Путь к JSON-хранилищу заявок; по умолчанию `<cwd>/src/lib/db/leads.json`, в serverless укажите `/tmp/leads.json` | `/tmp/leads.json` |
